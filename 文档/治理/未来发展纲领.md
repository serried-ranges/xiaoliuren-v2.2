# 未来发展纲领

> 目的：给后续维护一个稳定的方向与判定标准，避免「想到就加、加了就散」。
> 读者：维护者与协作者。本文回答「往哪走、什么不做、做到什么算完成」，不复制具体命令（命令见 [docs/开发者指南.md](../../docs/开发者指南.md)）。
> 事实来源：源码、测试、CI 与各文档；落地状态以[待办事项与方案进度](待办事项与方案进度.md)为准。
> 更新时间：2026-09-30

## 一、定位与不变的原则

V2.2 是**冻结的简洁兼容版**：保留 V2.1.2 的行为、排盘结果与备份格式，供旧结果核对与数据迁移验证。它不做预测承诺，也不替代专业意见。

不变的原则（任何改动都不得违反）：

1. **算对优先**：排盘算法可测试、可复现；界面可以朴素，卦象与旧版行为不能漂移；
2. **本地优先**：默认不联网；唯一外跳是用户主动点击「更多 → 切换标准」；
3. **兼容优先**：存储键名、导入导出格式与 V2.1.2 / V3 的互认关系是核心资产；
4. **删繁就简**：能在既有 12 个模块内解决，就不新增文件、依赖或平台；
5. **诚实表达**：不承诺准确，不把「受保护构建」说成保密，不把「测试通过」当作算法正确的证明；
6. **冻结从简**：归档期内只修正确性、安全与兼容问题，不新增功能与视觉。

## 三、能力边界（必须写清、不得含糊）

- 静态前端**无法保密**；本仓库不含密钥，也不接入任何 API；
- `localStorage` **不是**保险箱，也不是跨设备账号；身份隔离只对本浏览器有效；
- 受保护构建只提高阅读门槛，**不等于**加密或防逆向；
- 本仓库**没有**联网能力（随机起卦使用 `Math.random`，不调用网络或加密 API）；唯一外跳由用户主动触发；
- 核心测试是自包含副本，只代表规则回归，不代表真实页面行为验收。

## 四、演进方向

- **默认不演进**：保持冻结，修复兼容 / 安全 / 正确性问题；
- 若恢复活跃，须先过第六节的决策门槛，并按[接手与重启 §5](接手与重启.md)更新状态声明与门禁；
- 若 V3 需要 V2.2 的某项能力，走主项目「功能迁移单」流程，不直接复制代码、不承诺双向同步。

## 五、质量与门禁

CI（`.github/workflows/ci.yml`）要求以下全部通过：

| 关卡 | 覆盖 |
|---|---|
| `check` | 12 个源码模块语法 |
| `check:docs` | 文档相对链接无死链 |
| `test:all` | 5 个核心脚本（579 项断言） |
| `test:compat` | V2.2 ↔ V3.0 数据兼容（144 用例） |
| `build` / `build:protected` | 明码 / 受保护构建 |
| `test:protected` | 受保护包结构与可解码性（8 条断言） |

门禁原则：

1. **文档也是产物**：文档重构后必须过链接检查；
2. **发布必须逐次确认**：推送、导出与部署不随任务自动执行；
3. **门禁不是正确性证明**：测试通过只代表满足案例；排盘结论仍以人工核对与旧版对照为准；
4. **不新增第二条门禁链**：检查项并入现有 `check` / CI，不再造平行脚本。

## 六、决策门槛（满足才做，否则只写方案）

| 想做的事 | 启动门槛 |
|---|---|
| 解冻恢复开发 | 指定长期维护者与范围；更新[归档说明](../../归档说明.md)与 [CONTRIBUTING](../../CONTRIBUTING.md)；门禁全绿并补齐人工验收记录 |
| 修改排盘规则 / 数据契约 | 有对照样例与旧版行为对比；先更新[数据兼容与迁移](../../docs/数据兼容与迁移.md)与对应测试 |
| 引入新依赖或升级现有依赖 | 说明收益与回退方案；保持 `file://` 单文件交付不变；CI 全绿 |
| 新增平台或发布渠道 | 平台能力已验证；有独立测试与打包；明确长期维护者；不与 V3 发布链混用 |
| 恢复「模式持久化」等历史行为 | 先确认为行为修复而非新功能；给出与 V2.1.2 的行为对照与测试后再实施 |

## 七、数据与隐私红线

- 不收集、不上传、不代管任何用户数据；问念、记录与反馈只存本机；
- 不在任何产物中放置密钥、Token 或联系方式以外的个人信息；
- 文档与测试数据只使用脱敏或虚构案例。

## 八、非目标（明确不做）

- 不做「预测产品」，不承诺准确或替代专业意见；
- 不把 V2.2 重新包装成第三条活跃产品线；
- 不为「看起来更完整」加入第三方库、皮肤体系或后端；
- 不把历史资料中的旧结论、旧命令当作现行规范。

## 九、维护方式

1. 方向变化先改本文，再改各文档入口；进度与问题只在[待办事项与方案进度](待办事项与方案进度.md)登记；
2. 与本文冲突的旧方案以本文为准，并在对应位置标注为历史；
3. 新增或废止规则时，同步更新[文档/README.md](../README.md)的文档地图。
